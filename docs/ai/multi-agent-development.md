# 多 Agent 协同开发规范

> 状态：项目级协作流程权威文档  
> 原则：单一用户入口、动态委派、只读优先、默认单写入、独立验证、人工 Git 门禁

## 1. 角色模型

用户只与当前主 Agent 沟通。主 Agent 是职责，不是永久聊天窗口，负责：

- 澄清需求、目标、非目标和验收标准。
- 读取项目规则并检查当前工作树。
- 判断任务规模、风险和需要的子 Agent。
- 汇总调查结果并提出架构与 RIO。
- 等待用户批准关键决策。
- 冻结任务包、分配文件所有权和停止条件。
- 集成实际修改、组织验证和更新任务记录。
- 在人工 Git 门禁前停止。

项目提供四个基础子 Agent：

| 角色 | 默认权限 | 使用时机 |
| --- | --- | --- |
| code-explorer | 只读 | 调查入口、调用链、数据流、测试和复用点 |
| architecture-reviewer | 只读 | 审查边界、契约、RIO、迁移和兼容 |
| implementation-worker | 工作区写入 | 实现已经批准且边界明确的工作包 |
| validation-reviewer | 只读 | 独立检查最终 diff、测试和回归风险 |

安全、数据库、基础设施、性能、浏览器复现等专家按需临时增加。领域知识优先写入
架构文档，不持续堆入基础 Agent 配置。

## 2. 任务分级

### 小型任务

特征：范围清晰、低风险、不改变公共契约、通常只涉及少量文件。

流程：

~~~text
主 Agent 调查 → 实现 → 针对性验证 → 交付
~~~

默认不创建子 Agent。

### 中型任务

特征：涉及一个完整调用链或前后端中的多个文件，但架构边界稳定。

流程：

~~~text
只读调查 → 主 Agent 确认方案 → 单个实现 Agent → 主 Agent/独立验证
~~~

### 大型或高风险任务

特征：跨前后端、数据库、权限、基础设施或领域边界，或者包含迁移与兼容要求。

流程：

~~~mermaid
flowchart TD
  U["用户提出需求"]
  M["主 Agent 明确目标与非目标"]
  E["代码调查 Agent"]
  A["架构审查 Agent"]

  D["主 Agent 汇总方案与 RIO"]
  C["用户批准"]
  P["冻结任务包和契约"]
  W["默认一个实现 Agent"]
  V["独立验证 Agent"]

~~~

## 3. 调研与 RIO

中大型任务按以下顺序调查：

1. 检查工作树、项目规则和任务记录。
2. 搜索仓库内已有实现、依赖、测试和约定。
3. 确认仍存在知识缺口后，查询官方文档。
4. 必要时比较最多三个严肃的公开库或方案。
5. 对不确定的关键假设进行有时间边界的 Spike。
6. 输出架构方案和 RIO，等待用户批准关键选择。

公开库评估至少考虑兼容性、维护状态、安全、许可证、传递依赖、API 稳定性、
运维成本和退出策略。禁止未经用户批准引入新的生产依赖。

本项目 RIO 定义：

- Risks：失败模式、安全风险、技术债和未知项。
- Impact：对接口、数据、权限、性能、部署、兼容和用户体验的影响。
- Options：可选方案、取舍、推荐方案和回退路径。

## 4. 子 Agent 任务包

主 Agent 委派时只提供完成工作所需的最小上下文：

~~~text
任务目标：
非目标：
验收标准：
必读文档：
相关文件和入口：
已批准决策：
文件所有权：
允许的操作：
禁止的操作：
停止并上报条件：
返回格式：
~~~

停止并上报条件至少包括：

- 需求与架构或当前代码逻辑冲突。
- 必须修改未分配文件或公共契约。
- 发现用户/其他 Agent 的重叠修改。
- 测试失败原因超出工作包。
- 需要新依赖、迁移、权限或外部系统变更。

## 5. 并行与写入规则

- 默认最多同时运行三个子 Agent，日常优先使用一到两个。
- 优先并行代码调查、文档核实、测试分析和独立审查。
- 默认只有一个 Agent 写代码。
- 主 Agent 维护中央 delivery.md，子 Agent 写各自独立的 handoffs/*.md 或返回摘要。
- 多 Agent 不得同时修改同一个文件。
- 并行写入前必须冻结接口契约，并为每个 Agent 分配明确文件所有权。
- 大型独立写入使用不同 Git worktree；一个 worktree 对应一个分支和一个顶层 Codex 任务。
- .env.video.local 等被忽略的密钥文件不得自动复制到 worktree。
- 共享 Docker、数据库、端口和本地服务的最终集成验证必须串行执行。

## 6. 任务记录

大型任务使用：

~~~text
docs/changes/<任务编号>/
  delivery.md
  decisions.md
  verification.md
  handoffs/
~~~

- delivery.md：目标、状态、进度、修改范围、风险和下一步。
- decisions.md：用户批准的决策、备选方案、理由和影响。
- verification.md：已经实际执行的测试、结果和未验证项。
- handoffs/：子 Agent 的精简中文交接。

中央文档由主 Agent 单点维护。Git 保存实际提交历史，文档只保留重要提交引用，
不复制完整提交日志。

## 7. 上下文切换

主 Agent 是角色，不要求整个项目永久使用同一个对话。出现以下情况时建立检查点并
开启新的 Codex 任务：

- 一个阶段或独立功能已经完成。
- 对话积累大量日志、失败尝试或无关历史。
- 需求方向发生明显变化。
- Agent 开始重复、遗忘或混淆已批准决策。
- 准备从设计进入实现，或从实现进入独立集成验证。

切换前由旧主 Agent 更新任务档案，至少写清：

1. 已完成
2. 未完成
3. 当前风险
4. 下一步

新主 Agent 必须重新读取正式文档并检查当前 git status 和 git diff，不能盲信
旧摘要。长期连续性由仓库文档保障，不依赖聊天历史。

## 8. 验证与交付

验证 Agent 必须以批准的验收标准、权威架构、实际 diff 和当前测试为依据。问题等级：

- P0：安全、数据破坏、严重不可用，阻塞交付。
- P1：明确功能错误、权限漏洞、重大回归，阻塞交付。
- P2：重要但有规避方式的风险，应修复或由用户接受。
- P3：低风险改进，不阻塞交付。

最终交付必须包含：

- 修改文件和行为摘要。
- 已执行测试及真实结果。
- 未执行测试及原因。
- 残余风险和已知限制。
- 建议提交拆分和 commit message。
- 明确说明 AI 未执行暂存、提交、推送或 GitHub 操作。

## 9. 人工 Git 门禁

任何 Agent 都不能执行 Git 写操作或 GitHub 发布操作。主 Agent 只能在验证完成后向
用户提供建议，由用户本人检查 diff、暂存、提交、推送、创建和合并 PR。

如果未来需要更强的机械保证，可增加项目 Hook 或受管规则拦截 Git 写命令；启用前
应单独验证其对只读 Git 命令、构建工具和人工终端的影响。
