# 视频与传感器容量测试决策记录

## DEC-001：500 条/秒失败后停止更高档位

- 状态：已批准并执行
- 日期：2026-08-17
- 决策人：用户与主 Agent
- 背景：500 条/秒阶段 Gateway 连续报告 `Memory storage is full` 和设备数据无法保存，主机可用内存降至约 0.38 GB。
- 最终决定：立即停止 500 条/秒临时负载，不再运行 1000/3000 条每秒，等待积压排空并恢复 100 条/秒基线。
- Risks：继续施压会扩大遥测丢失、拖垮本地共享环境并污染结论。
- Impact：得到稳定下限 100 和失败上限 500，但没有得到 101-499 区间的精确拐点。
- Options：后续在独立压测机上以 150/200/300/400 条每秒二分；或先调优 Gateway 存储与批处理后复测。
- 回退方案：停止临时容器，暂停基线输入排空队列，再恢复原模拟器。
- 事实源影响：结果写入本任务 verification.md。

## DEC-002：区分摄像头源数与观看并发数

- 状态：已批准并执行
- 日期：2026-08-17
- 最终决定：40 路结果只表述为“单个 720p 源的 40 个并发观看者成功”，不表述为“支持 40 台摄像头”。
- 原因：每台摄像头会额外增加拉流、RTP 端口、解复用、录像和可能的转码成本，与同源扇出不同。

## DEC-003：以重复键回退更新闭环 WVP 并发登记竞态

- 状态：已执行并验证
- 日期：2026-08-18
- 背景：WVP 媒体服务器心跳采用先查询再插入，并发线程可同时判断记录不存在，导致后插入线程触发主键冲突。
- 最终决定：捕获首次插入的 `DuplicateKeyException` 并按同一 ID 执行更新；不在本轮引入数据库方言相关的 upsert SQL。
- Risks：异常回退会多一次数据库操作；若异常并非并发插入造成，更新结果仍需由后续心跳继续收敛。
- Impact：修复范围局限于媒体服务器登记服务，保持 Mapper 与公共接口契约不变；需为原本默认跳过的 WVP 测试提供显式开关。
- Options：选项一为数据库 upsert，原子性更直接但涉及 PostgreSQL/MySQL 多方言；选项二为 JVM 锁，无法覆盖多实例；本轮选择可移植的异常回退更新。
- 回退方案：移除异常捕获与 POM 测试属性即可恢复上游行为；数据库 schema 无变化。
- 验收：1/1 专项单测通过；当前源码镜像构建成功；运行时跨越多个心跳周期无重复键或数据完整性错误。
- 仓库边界：WVP 源码为主仓库忽略的嵌套 Git 仓库，必须单独人工提交。

## DEC-004：以现有 Video API 单摄像头闭环扩展多摄像头

- 状态：已批准并执行
- 日期：2026-08-29
- 决策人：用户
- 最终决定：使用多 Agent 只读核对现有前端、后端、媒体平台和容量证据，由主 Agent 汇总成可复用指南；新增摄像头继续遵守 `tbDeviceId + video_camera_binding + VideoProvider + 同源 HLS` 边界。
- Risks：把单源 40 观看者误写成 40 摄像头容量、复用同一个 `streamId`、遗漏客户权限或会话释放会造成错误串流、越权或资源泄漏。
- Impact：本轮只新增和更新中文文档，不改变 API、数据库 schema、权限或部署拓扑。
- Options：后续若需要批量状态或多宫格同时播放，应单独设计批量接口和容量测试，不能在本指南中静默扩展公共契约。
