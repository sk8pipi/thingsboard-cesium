Cesium 摄像头功能文件说明

说明

- 本文件作为摄像头相关功能的同步记录。
- 以后只要继续修改这套摄像头点位、视频预览、转流脚本、地图交互、Gateway 状态接入相关内容，都同步更新到这个文件。
- 当前记录包含首页地图和 Cesium 大屏编辑页面两套入口。
- 当前方案明确为“仅预览型摄像头”方案。
- 当前方案不包含控制能力，不包含 RPC，不包含 PTZ，不包含 ONVIF。
- 当前视频流继续走 `RTSP -> FFmpeg -> HLS -> http-server -> hls.js`，视频流本身不经过 Gateway。

文件列表与功能说明

1. src/views/tb/map/cameraTypes.ts
功能：
- 定义仅预览型摄像头的数据结构。
- 同时包含静态 attributes、动态 telemetry、地图点位兼容字段。
- 统一约束 cameraId、名称、经纬度、海拔、流地址、协议、状态、告警等级等字段。
- 提供 `CAMERA_ATTRIBUTE_KEYS`、`CAMERA_TELEMETRY_KEYS`、`resolveCameraStatus` 等运行时辅助能力。

2. src/views/tb/map/cameraMock.ts
功能：
- 提供当前摄像头示例数据。
- 给地图上的摄像头点位提供名称、位置、状态和浏览器可播放的 HLS 地址。
- 作为前端兜底静态点位数据源保留，不能删除。
- 当前默认播放地址为 `/live/camera-001/index.m3u8`。

3. src/views/tb/map/useCameraOverlay.ts
功能：
- 管理摄像头预览面板的打开、关闭和切换状态。
- 保存当前选中的摄像头。
- 与 runtime 合并后的 `cameraPoints` 配合工作。
- 后续如果扩展多个摄像头切换，可以继续复用这个 composable。

4. src/views/tb/map/useTbCameraRuntime.ts
功能：
- 前端摄像头运行时数据层。
- 优先从 ThingsBoard 获取摄像头 attributes 和 telemetry。
- 如果获取不到，则自动回退到 `cameraMock.ts`。
- 对 `deviceId` 做 UUID 校验，只有合法的 ThingsBoard 设备 ID 才会发起 attributes / telemetry 请求。
- mock 示例里的占位 `deviceId` 不会再触发 `Invalid UUID string` 请求错误。
- 本地 `playerError`、`previewOpenCount`、`previewLastOpenTs` 只有在值真实变化时才会更新，避免无效响应式重算。
- 合并策略明确区分：
  - `cameraMock.ts` 负责静态兜底点位
  - ThingsBoard 负责动态状态和可覆盖的静态属性
  - 前端本地 UI 状态负责当前会话的 `playerError`、`previewOpenCount`、`previewLastOpenTs`
- 对首页地图和大屏编辑页提供统一的 `cameraPoints` 数据源。

5. src/views/tb/map/CameraVideoPanel.vue
功能：
- 页面右上角固定定位的视频预览面板。
- 继续保留原有 `video + hls.js` 播放主逻辑，不替换现有视频方案。
- 显示摄像头名称、状态、位置说明和关闭按钮。
- 新增状态展示区，显示：
  - `online`
  - `streamAlive`
  - `bitrateKbps`
  - `lastHeartbeatTs`
  - `playerError`
  - `alarmText`
  - `alarmLevel`
  - `previewOpenCount`
- 在播放失败和恢复时向页面回传状态事件，供 runtime 更新本地 UI 状态。
- 对 `AbortError` 和自动播放拦截场景做了降噪处理，避免控制台持续刷屏。
- 对播放器错误 / 恢复事件做了去重，避免同一状态反复回传导致页面卡顿。
- 不新增任何控制按钮。

6. src/views/tb/map/CesiumMap.vue
功能：
- 在原有传感器点位之外，新增摄像头点位渲染能力。
- 为摄像头创建独立的 Cesium `CustomDataSource`。
- 使用 `Entity / Billboard` 在地图上显示摄像头图标和名称。
- 监听 Cesium 点击事件，区分传感器点位和摄像头点位。
- 点击摄像头点位时向外发出 `camera-click` 事件。
- 摄像头图标会根据运行时状态变化：
  - `online + streamAlive` 正常
  - `online + streamAlive=false` 异常

  - 有 `alarmLevel` 时高亮
- 点位 properties 中会保留摄像头状态字段，便于点击时直接带出预览数据。
- 地图只会在点位渲染相关字段变化时重绘，不会因为播放器错误文案或预览次数变化而整张图反复刷新。
- 点位重绘签名已改为稳定字符串，避免因为新数组引用导致误判为“需要重绘”。

整体流程说明

1. 摄像头提供 RTSP 地址。
2. `scripts/start-camera-hls.bat` 启动 FFmpeg，把 RTSP 转成 HLS。
3. 同一个脚本再启动 `http-server`，对外提供 `index.m3u8` 和 `ts` 分片。
4. 本地 adapter 检查 HLS 输出目录并通过 MQTT 发布摄像头状态。
5. ThingsBoard Gateway 通过 MQTT connector 接入摄像头 attributes 和 telemetry。
6. 前端通过 `useTbCameraRuntime.ts` 优先读取 ThingsBoard 数据，失败时回退到 `cameraMock.ts`。
7. 前端通过 `/live/camera-001/index.m3u8` 访问 HLS 地址。
8. 用户点击 Cesium 地图上的摄像头点位。
9. 右上角 `CameraVideoPanel` 打开并播放实时视频，同时展示运行时状态。

当前已知前提

- 前端不能直接播放 RTSP。
- 必须保证摄像头 RTSP 用户名、密码、路径正确。
- 只有 FFmpeg 成功生成 `index.m3u8` 后，前端视频才能正常播放。
- 当前版本只做预览和状态展示，不提供任何控制能力。

本次卡顿问题排查结论

- 之前点击摄像头点位后页面卡死，不是单一播放器错误，而是响应式更新链路叠加导致的“更新风暴”。
- 触发链路大致是：
  1. 点击摄像头点位，打开 `CameraVideoPanel.vue`
  2. 播放器初始化过程中触发自动播放、错误、恢复等状态变化
  3. `CameraVideoPanel.vue` 把这些状态回传给 `useTbCameraRuntime.ts`
  4. runtime 更新本地 `playerError`、`previewOpenCount`、`previewLastOpenTs`
  5. `cameraPoints` 重新计算
  6. `CesiumMap.vue` 误判为摄像头点位需要重绘
  7. Cesium 整张图反复重绘，页面出现明显卡顿甚至假死
- 当前已经通过下面几项修复切断这条链路：
  - 对 mock `deviceId` 做 UUID 校验，避免无效 telemetry 请求和错误回调
  - 对播放器 `AbortError` 和自动播放拦截场景做降噪
  - 对播放器错误 / 恢复事件做去重
  - 对 runtime 本地 UI 状态更新做“值没变化就不更新”
  - 对 Cesium 摄像头点位重绘改成稳定签名判断，只在真正影响点位显示的字段变化时重绘
- 现在页面不卡的原因，不是视频链路被替换，而是“播放器状态变化 -> runtime 更新 -> cameraPoints 重算 -> Cesium 重绘”的连锁反应已经被压住。

2026-05-05 HLS 401 supplement
- MediaMTX master playlist currently returns `audio2_stream.m3u8?session=...` and `video1_stream.m3u8?session=...`.
- If the frontend gives `index.m3u8` directly to `hls.js`, some browser + loader combinations may re-request the independent audio playlist without the `session` query and trigger `401 Unauthorized`.
- `src/views/tb/map/CameraVideoPanel.vue` now fetches the master playlist first, selects the first `#EXT-X-STREAM-INF` video media playlist, and then passes that session-bearing child playlist URL to `hls.js`.
- The master-playlist prefetch step must also seed the local HLS session cache with child playlist URIs; otherwise `hls.js` may re-issue `/live/.../video1_stream.m3u8` without query params and the loader will have no `session` value to restore.
- The current loader also pins the active primary video playlist URL. If `hls.js` later re-requests the same `video1_stream.m3u8` path without query params, the loader restores the full session-bearing URL instead of letting the request fall through to `401`.
